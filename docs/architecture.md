# Architecture

The Cargo workspace contains a headless discovery library, a terminal client and the Tauri host. Cargo's default members are the core and CLI so terminal development can run independently of WebKit or WebView2. The desktop renderer is a strict TypeScript and React Vite project.

| Component | Responsibility |
| --- | --- |
| `crates/stackrinse-core` | Project and artifact evidence, traversal policy, classifications, logical size inventory and a dry-run plan |
| `crates/stackrinse-cli` | Explicit roots, cancellation and terminal or JSON presentation |
| `apps/stackrinse-desktop/src-tauri` | Native folder and save dialogs, settings and history persistence, scan lifetime and renderer IPC |
| `apps/stackrinse-desktop/src` | Storage map, project navigation, candidate inspection, review, history and preferences |
| `apps/stackrinse-desktop/e2e` | Browser interaction checks using temporary inventories |
| `benchmarks` | Reproducible, disposable workspaces for traversal measurements |

## Data flow

A scan receives explicit roots, exclusions and protected project paths. Manifest discovery identifies a project and its ecosystems. Rules associate an ecosystem with candidate directory names, additional local evidence, expected rebuild consequences and qualitative cost. The engine reports absolute paths, classification explanations, file lengths, manifest modification times and warnings.

A project reports its effective protection and any mandatory repository-boundary reason. Each candidate reports whether its logical size is complete. The renderer uses these fields to explain protection and partial measurements.

The CLI formats the report directly. The native desktop host runs traversal outside the UI thread and forwards throttled progress events. The renderer uses the report for the category ring, sorting and detailed inspection. Only the native side touches the filesystem. Selecting a candidate for review does not grant a capability to delete it.

## Review snapshots

The core constructs an owned `Plan` from complete, eligible candidates in one report. Its Rust accessors expose a slice and a logical-byte total. CLI JSON and desktop IPC preserve the snapshot fields. Each nonempty change to the review selection requests a fresh plan from the host, which intersects the requested paths with the scan and current protections. Clearing the selection discards the preview.

Report totals are calculated when requested so a filtered CLI view and its JSON totals refer to the same projects. Discovery keeps the full inventory in memory. The explorer shows 40 projects per page and detail and review views show up to 20 candidates per page.

## Local state

The desktop uses Tauri's per-user application configuration directory for `dev.klowzy.stackrinse`. Its settings JSON contains absolute paths, exclusions, protected project paths and appearance preferences. Updates validate the configuration and replace it via a sibling temporary file under a lock. The live scan and dry-run input stay in memory. CLI JSON is written to stdout and can contain full paths.

### Scan history

The desktop stores `scan-history.sqlite3` in Tauri's per-user local application data directory. Bundled SQLite provides transactions, cross-process coordination and versioned schema upgrades. Summary rows are indexed by completion time and can be read without loading project details. Insertion and pruning commit together. The default retention is 50 scans and the UI offers up to 100. The database prunes oldest entries above 24 MiB of encoded records and caps its main file at 32 MiB. SQLite may create a temporary rollback journal during a write. Large snapshots retain totals and breakdowns when project details exceed their budget.

History stores roots, exclusions, warnings, counts, durations, and aggregate project, ecosystem and category observations. The saved scope key is a digest of the canonical, deduplicated roots, normalized exclusions and protections, and the core `DISCOVERY_RULE_VERSION`. Increment that constant when discovery, attribution, or measurement changes affect comparisons. Sprint 4 records retain their fingerprints and read as version 1. Current scans and exports report their rule version explicitly. Project comparisons match paths. Ecosystem bytes follow each artifact's discovery rule, and conflicting evidence is reported once in its own bucket. Scan warnings and incomplete candidate sizes block comparisons. Cancelled and failed scans are excluded from history.

Unreadable, unrecognized or newer databases are preserved. A persistence failure is reported independently of the live scan. To start a fresh database after corruption, close StackRinse and move its history file and any companion journal out of the app data directory together. Keep the originals if recovery is needed. OS user permissions and a trustworthy app data directory are assumed.

Exports are generated by the native host from a live or saved observation, with JSON and spreadsheet-safe CSV formats. A native Save dialog supplies the destination, and the report is written to a temporary sibling and published only after serialization succeeds. Existing files are preserved. The renderer supplies a report source and format.

## Extending discovery

Add an ecosystem marker and describe the artifact's required evidence in the core rule table. Marker groups can require one marker or a conjunction. Nested markers inspect each ancestor before looking for the leaf. Cache signatures use small reads through no-follow file handles. The scanner retains the observed marker evidence for protected artifacts and checks the original marker again before allowing review. Include a tool-generated fixture and lookalikes with absent evidence, tracked content, links, ambiguous files and nested projects. Keep executable project commands outside discovery.
